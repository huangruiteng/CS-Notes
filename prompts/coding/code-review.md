# Code Review Prompt

适用场景：和 AI 一起 review Merge Request / Pull Request。默认使用 GitLab `glab`，可按仓库替换成 `gh`。

```text
我想请你和我一起进行 code review。

首先请执行 `glab mr checkout $MR_ID` 命令，切换到对应的代码分支，并确保内容是最新的。再通过 `glab mr view $MR_ID | cat` 和 `glab mr diff $MR_ID | cat` 命令来获取 merge request 中的修改内容。

然后，请开始一步一步深入思考，仔细执行如下 code review 流程。如果改动比较简单直接，你也可以自行选择跳过某些步骤。

1. 理解业务目标：判断你是否能理解这个改动的业务目标。
2. High-level review：查看当前项目内容，本次改动是否放在合适位置，是否尽可能复用已有实现，是否可能破坏现有设计与逻辑。
3. 检查 Bug：仔细分析当前代码修改，是否隐含业务错误、逻辑纰漏或安全问题。对于没有修改但相关联的代码，也需要检查是否有遗漏。
4. 代码清晰度：评估代码设计，逻辑是否简洁易懂，命名是否清晰合理。假设一年后再来读这几行代码，是否能轻松理解。
5. KISS 原则：审视每一行代码是否简洁、清晰，没有不必要复杂度，尤其避免重复造轮子。检查是否有没用到的定义、过于复杂的逻辑、过多参数等问题。
6. 单一职责：函数/类是否只做一件事，职责是否明确，项目结构是否清晰。注意控制文件、类、方法的代码行数。
7. 测试覆盖：复杂业务逻辑必须有相应测试。但不要过度测试，例如没有 if/else/for 等控制逻辑的代码，不需要写测试。一般只对 public 方法写测试。

完成整个流程后，请对 code review 中发现的重点问题进行总结，以中文输出。
```
