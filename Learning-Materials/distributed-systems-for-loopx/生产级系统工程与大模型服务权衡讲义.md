## 阅读地图与五步架构作答法

面对任何没有唯一标准答案的生产系统设计或疑难排障问题，统一按以下五步拆解，避免遗漏关键工程维度：

1. **约束条件与容量算术（Constraints & Capacity Math）**：明确 QPS、并发流数、单连接状态体积、读写比、P99 延迟预算与一致性等级，先算出瓶颈落在 CPU、DRAM 容量、HBM 带宽、磁盘 IOPS 还是跨机网络 RTT。
2. **单一事实源与状态不变量（Authority & Invariants）**：区分「外部世界状态」「本地观测知识」「当前执行授权」（详见[补课讲义 §1](./补课讲义.md#1-一个动作的三种事实)），定义 CAS 版本号、租约与单调递增 Fencing Token 的合法转换条件。
3. **模块化核心伪代码 / 手抄原语（Clean Core Primitives）**：用 30–50 行无歧义代码表达最核心的缓冲区游标、水位抢占或原子同步回路，显式标出锁粒度、背压（Backpressure）阈值与超时分支。
4. **故障模式与幂等恢复边界（Crash, Disconnect & Retry Recovery）**：逐项推演客户端断网重连、进程 `SIGKILL` / OOM、GC 或调度器长暂停（STW）、下游流式卡死与超时重试时的恢复路径。
5. **方案取舍与 10× 扩展拐点（Trade-offs & Scaling Limits）**：主动指出当前方案牺牲了什么，流量或状态膨胀 10 倍时哪一层最先击穿，以及对应的拆分演进条件。

## 1. Linux 内核、虚拟内存与高性能网络底层排障

本节覆盖生产环境最常引发尾延迟毛刺、内存暴涨与连接耗尽，却容易被高层框架掩盖的操作系统与网络协议细节。

### 1.1 虚拟内存、CoW `fork` 毛刺与 `cgroup` OOM 真相

| 机制 | 核心物理过程与数量级 | 常见生产事故与反例 | 工程根治手段 |
| --- | --- | --- | --- |
| **x86-64 四级页表与 TLB** | 48-bit 虚拟地址按 `9+9+9+9+12` 切分（4KB 页）；TLB 未命中需走 4 次页表访存（无缓存时叠加数百 ns）；跨核 `munmap`/`mprotect` 触发 IPI **TLB Shootdown** | 大内存引擎高频申请/释放小块映射导致多核系统态 `%sys` 飙升 | 预分配内存池（Arena / Slab），或对大块连续区域启用 **2MB HugePages**（少走一级页表、大幅降低 TLB Miss） |
| **`fork()` Copy-on-Write (CoW)** | `fork` 仅复制页表并将父子进程页表项标为只读；随后任一侧写该页即触发缺页中断（Page Fault）复制整张 4KB 物理页 | 几十 GB 内存的 Python / Redis / 推理主进程直接 `fork()` 跑子命令或落快照：主进程高频处理请求改写对象引用计数（如 Python `PyObject` 头部 `ob_refcnt`！），数秒内触发海量 CoW 缺页风暴，P99 延迟飙升百倍甚至触发 OOM | 用 `posix_spawn` / `vfork + exec` 替代裸 `fork`；长驻进程把外部命令委托给预先 fork 好的轻量 Zygote / Sidecar 守护进程；Python 多进程优先 `spawn` 或把只读大数据放 `mmap` 共享内存 |
| **Page Cache、`O_DIRECT` 与 `cgroup v2`** | 普通 `write()` 写入内核 Page Cache 即返回（不等落盘，掉电会丢，需 `fsync`）；内核后台 `pdflush` 触及 `vm.dirty_ratio` 时同步阻塞写线程 | 容器监控告警内存逼近 95% 以为内存泄漏，实为大文件顺序读写撑满 `cgroup` 内的 Page Cache；但若匿名页（RSS）+ 不可回收页超限，OOM Killer 会直接 `SIGKILL (-9)` 主进程 | 区分 `anon`（真实堆内存）与 `file`（可回收 Page Cache）；自建缓存池的数据库/存储引擎用 `O_DIRECT` 绕过双缓冲；写密集日志控制 `dirty_background_bytes` 平滑刷盘 |

### 1.2 `epoll` 内核双结构、LT/ET 与惊群演进

`epoll` 高效的根源在于把 `select/poll` 每次调用时的 $O(N)$ 全量句柄拷贝与线性扫描拆成了两步：
1. `epoll_ctl` 在内核**红黑树（RB-Tree）**上增删改监控目标（$O(\log N)$），并向网卡/管道等待队列注册回调 `ep_poll_callback`；
2. 硬件中断数据就绪时，回调把该 `epitem` 直接挂入就绪**双向链表 `rdlist`**，$O(1)$ 唤醒 `epoll_wait` 只拷回活跃事件。

- **LT（Level-Triggered，默认水平触发）vs ET（Edge-Triggered，边缘触发）**：
  - LT 只要内核接收缓冲区还有未读字节，下次 `epoll_wait` 仍会返回；编程安全、不易漏事件。
  - ET 仅在状态「从无到有 / 新字节到达」边缘通知一次。**使用 ET 必须绑定非阻塞 fd（`O_NONBLOCK`）并在每次通知时循环 `read/accept` 直到返回 `EAGAIN / EWOULDBLOCK`**；若只读一半就退出循环，且对端不再发新包（正在等你的响应），连接将永久死锁饥饿。
  - 多工作线程共享同一监听 fd 时：早期多线程 `epoll_wait` 存在唤醒惊群，现代内核通过 **`EPOLLEXCLUSIVE`** 限制单次唤醒队列前缀，或直接启用 **`SO_REUSEPORT`** 由内核按四元组哈希在多个独立监听 socket 间均衡分发。

### 1.3 TCP 连接状态机、队头阻塞与流式网关排障

```text
常见线上连接异常三秒定性：
1. 服务端堆积海量 CLOSE_WAIT  --> 100% 是本端应用代码 Bug（对端已发 FIN，本端忘记调用 close() 释放 fd，检查异常分支或连接池泄漏）。
2. 客户端/反代堆积海量 TIME_WAIT --> 主动关闭短连接过多（2MSL 等待防历史迷途包混入新连接）；优先改 HTTP Keep-Alive / gRPC 长连接池，辅以 net.ipv4.tcp_tw_reuse=1（绝不在 NAT 环境开已废弃的 tcp_tw_recycle！）。
3. 偶发连接超时 / SYN 重传丢包 --> 检查 netstat -s 中 listen drops：全连接队列受 min(backlog, net.core.somaxconn) 限制，应用层主事件循环若被重 CPU 阻塞未及时 accept()，全连接队列满即静默丢弃握手完成包。
```

- **HTTP/1.1 → HTTP/2 → HTTP/3 (QUIC) 的队头阻塞（HOL Blocking）迁移**：
  - HTTP/2 在单个 TCP 连接内做二进制帧多路复用（Stream Multiplexing），解决了 HTTP/1.1 应用层串行等待，但**引入了更隐蔽的 TCP 传输层队头阻塞**——只要物理链路丢 1 个 TCP 包，内核协议栈为保字节流总序，会卡住该连接上**所有并发 Stream** 等待重传；高丢包弱网下吞吐甚至劣于多条独立 HTTP/1.1 连接。QUIC 基于 UDP 在用户态按 Stream 独立编号重传，彻底隔离跨流丢包。
- **长程 Agent 流式网关（SSE / WebSocket）生产三铁律**：
  1. **反代零缓冲透传**：Nginx 转发 SSE 必须显式配置 `proxy_buffering off; X-Accel-Buffering: no;`，否则流式 Token 会被攒够 4KB/8KB 才吐给前端，造成“假卡死”。
  2. **断线游标幂等续传（`Last-Event-ID` / `seq_id`）**：长任务持续数十分钟，移动网/Wi-Fi 切换必断连。服务端必须把输出写入带单调 `seq_id` 的只追加日志（Append-Only Event Log），客户端重连携带 `after_seq`，网关先重放增量事件再无缝切回实时流。
  3. **防重连雪崩（Full Jitter）**：网关滚动重启瞬间数万长连接同时断开，客户端禁止固定间隔重试，必须采用指数退避加全随机抖动：
     $$\text{sleep} = \text{Uniform}\bigl(0,\ \min(\text{cap},\ \text{base} \cdot 2^{\text{attempt}})\bigr)$$

## 2. 硬件并发内存模型、原子序与 Rust/Python 并发安全

### 2.1 为什么没有锁时直觉会失效：Store Buffer 与伪共享

- **StoreLoad 乱序（连强内存序 x86 TSO 都会发生！）**：每个 CPU 核写变量时先写入私有 **Store Buffer** 再异步刷入 L1 Cache，而读其他变量直接查 Cache。若核 0 执行 `X = 1; r1 = Y`，核 1 执行 `Y = 1; r2 = X`（初值均为 0），即使指令未重排，两边都可能从自己的 Store Buffer 尚未刷出前读到对方的旧值 `r1 == 0 && r2 == 0`！只有 `SeqCst`（插入 `mfence` 或 `lock` 前缀原子指令清空 Store Buffer）能阻止该现象。
- **伪共享（False Sharing）**：CPU 缓存一致性协议（MESI）锁定的最小粒度是一条 **64 字节 Cache Line**。若生产者频繁写的 `tail` 与消费者频繁写的 `head` 紧挨着放在同一结构体（共占 16 字节），两颗核会以每秒千万次互相把对方的 L1 Cache Line 置为 `Invalid`，延迟从 `~4ns` 退化到跨核 `~40–80ns`。解法：用 `#[repr(align(64))]`（Rust）或 `alignas(64)`（C++）将高频独立写指针物理隔离到不同缓存行。

### 2.2 原子内存序三层精准判定表（多选题高频考点）

| 内存序（Rust / C++） | 编译器与硬件语义 | 典型合法场景 | 常见误用反例 |
| --- | --- | --- | --- |
| **`Relaxed`** | 仅保证该原子变量自身的读写不可撕裂且单变量修改顺序一致；**不提供任何跨变量可见性同步** | 全局监控指标计数 `metrics.fetch_add(1, Relaxed)`、已知仅当前线程独占写的本地游标读取 | 用 `Relaxed` 写 `ready = true` 通知另一线程读非原子 `data`（必有未定义行为 / 读到未初始化脏数据！） |
| **`Release`（写）+ `Acquire`（读）** | 线程 A 对原子变量 $M$ 执行 `store(..., Release)` 之前的所有普通/原子内存写入，对随后看到该值的线程 B `load(Acquire)` **全部可见（Happens-Before）** | **单生产者单消费者无锁环形队列（SPSC Ring）**、自旋锁加解锁、`Arc` 引用计数递减（`fetch_sub(1, Release)` 配合归零分支 `fence(Acquire)` 后析构！） | 为什么 `Arc::drop` 不能只用 `Relaxed`？因为析构线程在销毁内部数据前必须看见其他所有线程在放弃引用前对该数据的最后修改！ |
| **`SeqCst`** | 在 `Acquire/Release` 基础上，强制所有核对所有 `SeqCst` 操作观测到**唯一的全局总序** | 双边标志位互检（Dekker / Peterson 唤醒协议：先写 `queue_non_empty` 再读 `worker_sleeping`） | 在热路径无脑全用 `SeqCst` 白交硬件屏障税 |

### 2.3 双语言对照手抄原语（一）：流式半包解析与异步取消安全（Python vs Rust）

**为什么异步 `select!` 取消安全（Cancellation Safety）是资深工程必考坑？**
在 Rust `tokio::select!` 或 Python `asyncio.wait(..., return_when=FIRST_COMPLETED)` 中，当超时或控制信号抢先完成时，正在等待网络读取的分支 Future 会被**直接 `drop` / `cancel`**。如果解码器把“读了一半尚未遇到分隔符的字节”存在异步函数内部的**栈局部变量**里，取消瞬间这半包字节将永久丢失，后续重入读取立即产生协议错位！

**正确范式**：将残余缓冲区提升为状态机结构体字段（Struct-owned Residual Buffer），并用游标摊销 $O(1)$ 切片开销，同时设置 `max_frame_bytes` 硬上限防止恶意无分隔符长流打爆内存。

#### Python 3 标准手抄版（零拷贝游标 + 防 OOM 帧上限）

```python
class ChunkedFrameStreamParser:
    def __init__(self, max_frame_bytes: int = 65536, delimiter: bytes = b"\n") -> None:
        self._max = max_frame_bytes
        self._delim = delimiter[0]
        self._buf = bytearray()
        self._pos = 0

    def feed(self, chunk: bytes) -> list[bytes]:
        self._buf.extend(chunk)
        frames: list[bytes] = []
        while True:
            nl = self._buf.find(self._delim, self._pos)
            if nl == -1:
                if len(self._buf) - self._pos > self._max:
                    self._buf.clear()
                    self._pos = 0
                    raise ValueError("unterminated frame exceeds max_frame_bytes")
                break
            if nl - self._pos > self._max:
                self._buf.clear()
                self._pos = 0
                raise ValueError("frame exceeds max_frame_bytes")
            frames.append(bytes(self._buf[self._pos : nl]))
            self._pos = nl + 1

        if self._pos >= 4096 and self._pos * 2 >= len(self._buf):
            del self._buf[: self._pos]
            self._pos = 0
        return frames
```

#### Rust 标准手抄版（`#[repr(align(64))]` 无锁 `Acquire/Release` SPSC 队列 + RAII 防泄漏守卫）

```rust
use std::cell::UnsafeCell;
use std::mem::MaybeUninit;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

#[repr(align(64))]
struct PaddedIndex(AtomicUsize);

pub struct SpscRing<T, const N: usize> {
    head: PaddedIndex, // consumer writes, producer Acquire-loads
    tail: PaddedIndex, // producer writes, consumer Acquire-loads
    slots: [UnsafeCell<MaybeUninit<T>>; N],
}

unsafe impl<T: Send, const N: usize> Send for SpscRing<T, N> {}
unsafe impl<T: Send, const N: usize> Sync for SpscRing<T, N> {}

impl<T, const N: usize> SpscRing<T, N> {
    pub fn try_push(&self, val: T) -> Result<(), T> {
        let tail = self.tail.0.load(Ordering::Relaxed);
        let next = (tail + 1) % N;
        if next == self.head.0.load(Ordering::Acquire) {
            return Err(val); // full
        }
        unsafe { (*self.slots[tail].get()).write(val); }
        self.tail.0.store(next, Ordering::Release); // publish payload before index!
        Ok(())
    }

    pub fn try_pop(&self) -> Option<T> {
        let head = self.head.0.load(Ordering::Relaxed);
        if head == self.tail.0.load(Ordering::Acquire) {
            return None; // empty
        }
        let val = unsafe { (*self.slots[head].get()).assume_init_read() };
        self.head.0.store((head + 1) % N, Ordering::Release);
        Some(val)
    }
}

/// Panic-safe & async-cancel-safe RAII permit guard:
pub struct PermitPool { available: AtomicUsize }
pub struct PermitGuard { pool: Arc<PermitPool>, n: usize }

impl Drop for PermitGuard {
    fn drop(&mut self) {
        self.pool.available.fetch_add(self.n, Ordering::Release);
    }
}
```

## 3. 存储引擎、事务隔离完整谱系、分布式共识与跨服务一致性

日常做高层架构或交由 AI 编码很容易产生“概念熟悉感错觉”——听说过名词，但闭卷面对具体并发交错或节点崩溃序列时难以精确判定边界。本章从单机存储引擎一直推到分布式共识与跨系统事务。

### 3.1 单机存储双引擎：B+Tree 原地更新 vs LSM-Tree 追加合并

| 维度 | **B+Tree（InnoDB / PostgreSQL 索引）** | **LSM-Tree（RocksDB / LevelDB / Pebble）** |
| --- | --- | --- |
| **写入路径** | 先顺序写 `WAL`（Redo Log），再随机修改缓冲池（Buffer Pool）中的 16KB 页，后台刷脏页；页分裂需加锁 | 顺序追加 `WAL` + 写入内存有序表 `MemTable`（SkipList）即返回；写满冻结为 `Immutable MemTable` 顺序刷盘成不可变 `SSTable (L0)` |
| **读取路径** | 沿 3–4 层树高按二分定位叶子页，点查与范围扫描极稳定（最多 1–2 次磁盘随机读） | 依次查 `MemTable` $\rightarrow$ `L0`（键范围可能重叠，需遍历各 L0 文件！）$\rightarrow$ `L1..Lk`（每层键不重叠，二分定位）；**强依赖每块 SSTable 的内存 Bloom Filter 提前过滤不存在的键** |
| **放大权衡** | **读放大低**；随机写导致**写放大高**（改几十字节刷整张 16KB 页 + Doublewrite Buffer）且页内存在约 1/3 空间碎片 | **写吞吐极高**（随机写转顺序写）；代价是后台 **Compaction（归并排序清墓碑）带来周期性 CPU/IO 尖峰**，若 L0 堆积超过阈值会触发 **Write Stall（写限速甚至阻塞停顿）** |
| **Compaction 流派** | — | **Size-Tiered**（相近大小合并，写放大低，空间放大达 $2\times$）；**Leveled**（RocksDB 默认，$L_{i+1}=10 L_i$，空间放大仅 `~1.1x`、读放大低，写放大较高） |

### 3.2 五大并发异常与事务隔离级别完整对照表

1. **脏读（Dirty Read）**：$T_2$ 读到了 $T_1$ **尚未提交**的修改（随后 $T_1$ 回滚，$T_2$ 拿到幽灵脏值）。`READ COMMITTED` 即可消除。
2. **不可重复读与读偏序（Read Skew）**：
   - 场景：Alice 两张卡各 `500` 元（总额 `1000`），$T_1$ 从卡 A 转 `100` 到卡 B。
   - 在 `READ COMMITTED` 下：审计事务 $T_2$ 先读卡 A 得 `500`；随后 $T_1$ 提交（A=`400`, B=`600`）；$T_2$ 再读卡 B 得 `600`，算出总额 `1100`！跨行不变量在同一次只读观察中破裂。**MVCC 快照隔离（`REPEATABLE READ`）让事务全程读取启动瞬间的一致性快照，彻底消除 Read Skew**。
3. **丢失更新（Lost Update）**：两事务并发执行 `SELECT v -> 内存算出 v+1 -> UPDATE v`（如扣库存、累加计数），后写者覆盖先写者：
   - **高频陷阱**：MySQL InnoDB 的默认 `REPEATABLE READ` **不能自动阻止普通读后写的丢失更新**！PostgreSQL 的 `REPEATABLE READ` 会在提交时检测同行并发写冲突并报错回滚后者（First-Committer-Wins）。通用安全解法：**原子单句 `UPDATE t SET v = v + 1`**、**CAS 条件更新 `WHERE version = old_v`** 或 **`SELECT ... FOR UPDATE`**。
4. **幻读（Phantom）与写偏序（Write Skew）**：
   - **写偏序反例**（两事务读同一集合，但**各自写不同行**）：医院要求至少 $\ge 1$ 名医生在岗（当前 Alice、Bob 均在岗）。$T_1$ 与 $T_2$ 在同一 MVCC 快照下各自查到在岗数为 `2`，于是 $T_1$ 改 Alice 行请假提交、$T_2$ 改 Bob 行请假提交——**因修改的是不同行，行级写冲突检测完全不触发**，结果在岗人数变为 `0`！
   - **三种根治手段**：① 升级 **`SERIALIZABLE`（PostgreSQL 用 SSI 追踪 `rw-antidependency` 环路；MySQL 退化为读写锁）**；② 悲观锁物化读集 `SELECT ... FOR UPDATE`（InnoDB 用 **Next-Key Lock = Record Lock + Gap Lock** 锁住索引间隙阻断幻影插入）；③ **物化冲突锚点行**：抽出单行排班摘要做 CAS 版本递增。

### 3.3 复制、Quorum 盲区与 Raft 共识三大安全性定理

1. **为什么无主复制满足 $W + R > N$ 仍【不保证】线性一致性（Linearizability）？**
   - 设 $N=3, W=2, R=2$，三个经典反例：① **并发写读竞态**：新值 $x=1$ 刚写入 A（未到 B、C），读 $R_1$ 命中 `(A=1, B=0)` 返回 `1`，紧接着读 $R_2$ 命中 `(B=0, C=0)` 却退回 `0`（除非读返回前同步完成 Read Repair 写回多数派）；② **部分写失败未回滚**：写仅在 1 个节点落盘即报错返回失败，但该脏副本仍可被后续读看到；③ **Sloppy Quorum** 网络分区借用临时节点期间重叠失效。
2. **Raft 共识算法闭卷必考三条铁律**：
   - **选举限制（Election Restriction）**：Candidate 日志必须至少与多数派一样新才能获票，新旧按 **`(lastLogTerm, lastLogIndex)` 字典序**比较（先比最后一条 Term，Term 相同再比长度 Index）：
     $$(t_{\text{cand}},\, i_{\text{cand}}) \ge (t_{\text{voter}},\, i_{\text{voter}}) \iff (t_{\text{cand}} > t_{\text{voter}}) \lor (t_{\text{cand}} == t_{\text{voter}} \land i_{\text{cand}} \ge i_{\text{voter}})$$
   - **日志匹配归纳律（Log Matching）**：两节点同一 `index` 处 `term` 相同，则其及之前全部前缀日志必完全相同（由 `AppendEntries` 校验 `(prevLogIndex, prevLogTerm)` 保证）。
   - **Figure 8 旧 Term 提交禁令（压轴必考点！）**：新当选的 Term 4 Leader 发现一条遗留的 **Term 2 日志**已存在于多数派节点——**绝对禁止直接将其标为 Committed！** 因为若该 Leader 随即崩溃，某持有 `(term=3)` 尾日志的节点仍可合法当选 Term 5 Leader 并覆写该 Term 2 日志。**唯一合法规则**：新 Leader 上任后必须先写入并复制到多数派至少一条**当前 `currentTerm` 的日志（如一条 `no-op` 空日志）**，借日志匹配律间接提交所有历史前缀。

### 3.4 跨服务一致性：2PC 阻塞缺陷 vs Transactional Outbox vs Saga

- **为什么高并发在线系统忌用 2PC**：Prepare 阶段所有参与者锁死资源等待协调者指令，协调者一旦单点故障或网络抖动，参与者连接池全部卡死在 `In-Doubt` 状态。
- **Transactional Outbox（本地事务消息表，工业界首选）**：将「更新业务表」与「向同库 `outbox` 表插入事件记录」放入**同一本地数据库事务**原子提交；后台 Relay 扫描未投递事件发往下游并标 `SENT`，下游凭 `event_id` 幂等去重。
- **Saga 正反向补偿三防线**：拆为局部事务链 $T_1 \dots T_k$ 与逆向补偿 $C_{k-1} \dots C_1$，必须同时实现 **① 空补偿防护**（原请求未达时补偿落墓碑空过）、**② 防悬挂**（空补偿墓碑存在时拒绝迟到的原正向请求）、**③ 补偿幂等**。

### 3.5 双语言对照手抄原语（二）：Fencing 幂等账本（Python）与嵌套事务 Undo Log（Rust）

单靠“分布式锁 TTL”防不住旧 Worker GC STW 暂停醒来写脏数据（详见[补课讲义 §10](./补课讲义.md#10-租约fencing-与旧执行者)），存储层必须核验单调递增 `fencing_token` 与 `op_id` 幂等状态。

```python
class FencedIdempotentLedger:
    def __init__(self, ttl_ms: int = 5000) -> None:
        self._ttl, self._epoch, self._max_token = ttl_ms, 0, 0
        self._owner: str | None = None
        self._expires_at = 0
        self._ops: dict[str, list] = {}  # op_id -> [payload_hash, state, token, result]
        self._kv: dict[str, object] = {}

    def acquire_lease(self, worker: str, now_ms: int) -> int | None:
        if self._owner and self._owner != worker and now_ms < self._expires_at:
            return None
        self._epoch += 1
        self._owner, self._expires_at = worker, now_ms + self._ttl
        self._max_token = max(self._max_token, self._epoch)
        return self._epoch

    def _fence(self, token: int) -> None:
        if token < self._max_token:
            raise PermissionError(f"stale fencing token {token} < {self._max_token}")
        self._max_token = token

    def begin_or_replay(self, op_id: str, payload_hash: str, token: int) -> tuple[str, object]:
        self._fence(token)
        rec = self._ops.get(op_id)
        if rec is None:
            self._ops[op_id] = [payload_hash, "IN_FLIGHT", token, None]
            return "EXECUTE", None
        if rec[0] != payload_hash:
            raise ValueError("idempotency key reused with mismatched payload")
        if rec[1] == "COMMITTED":
            return "COMMITTED", rec[3]
        if token > rec[2]:
            rec[2] = token
            return "EXECUTE", None
        return "IN_FLIGHT_OTHER", None

    def commit_write(self, op_id: str, token: int, key: str, val: object, res: object) -> None:
        self._fence(token)
        rec = self._ops.get(op_id)
        if rec is None or rec[2] != token:
            raise PermissionError("not current fenced owner of operation")
        if rec[1] != "COMMITTED":
            self._kv[key] = val
            rec[1], rec[3] = "COMMITTED", res
```

**嵌套事务 Savepoint Undo Log 核心不变量（Rust）**：内层子事务 `commit()` 时**绝不能清空 `undo` 栈**，只能弹出 savepoint 将变更并入父事务；仅当最外层根事务 `commit()` 时才清空 `undo`。

```rust
use std::collections::HashMap;
use std::hash::Hash;

pub struct NestedTxnKv<K, V> {
    data: HashMap<K, V>,
    undo: Vec<(K, Option<V>)>,
    savepoints: Vec<usize>,
}

impl<K: Eq + Hash + Clone, V: Clone> NestedTxnKv<K, V> {
    pub fn set(&mut self, key: K, val: V) {
        let prev = self.data.insert(key.clone(), val);
        if !self.savepoints.is_empty() {
            self.undo.push((key, prev));
        }
    }
    pub fn begin(&mut self) { self.savepoints.push(self.undo.len()); }
    pub fn commit(&mut self) -> bool {
        if self.savepoints.pop().is_none() { return false; }
        if self.savepoints.is_empty() { self.undo.clear(); }
        true
    }
    pub fn rollback(&mut self) -> bool {
        let Some(sp) = self.savepoints.pop() else { return false; };
        while self.undo.len() > sp {
            let (k, old) = self.undo.pop().unwrap();
            match old {
                Some(v) => { self.data.insert(k, v); }
                None => { self.data.remove(&k); }
            }
        }
        true
    }
}
```

## 4. 大规模高并发在线服务架构全链路复习

### 4.1 缓存四大灾备与 Cache-Aside 脏回填竞态推演

| 问题 | 触发场景 | 标准组合拳解法 |
| --- | --- | --- |
| **缓存穿透（Penetration）** | 海量请求查询数据库里**根本不存在**的恶意 ID，每次都绕过缓存直击 DB | ① 前置 **Bloom Filter**（注意不支持直接删除，需删时用 Counting BF 或 Cuckoo Filter）；② 对空结果缓存短 TTL（如 30s 空哨兵） |
| **缓存击穿 / 惊群（Stampede）** | 某个超高频热点 Key 过期瞬间，成千上万并发请求同时未命中并涌入 DB 重算 | **SingleFlight（进程内合并同 Key 并发回源 Future）+ 分布式互斥 Lease Token**（仅 1 个请求回源写库，其余短暂等待或返回旧值异步刷新 Stale-While-Revalidate） |
| **缓存雪崩（Avalanche）** | 大批 Key 在同一时刻集中过期，或缓存集群某分片宕机 | 过期时间加随机抖动 `TTL + Uniform(0, jitter)` + 进程内小容量 L1 本地缓存（TinyLFU / LRU）兜底 + 降级限流 |
| **超级热 Key 打爆单分片** | 单 Key 流量达数十万 QPS，打满单个 Redis 分片网卡/单核 CPU | 客户端 SDK 热点探测自动晋升**本地极短 TTL 内存缓存**，或将 Key 拆成 `key#0 .. key#(K-1)` 多副本散列到全部节点读取 |

- **为什么「先删缓存，再写数据库」必出脏数据，而标准「先写数据库，再删缓存」仍有极低概率脏回填？**
  - 若**先删 Cache 再写 DB**：写线程 $W$ 刚删完 Cache 还没提交 DB，读线程 $R$ 立刻未命中读出 DB 旧值回填进 Cache——此后直到过期前缓存永远锁死脏旧值（高频必现！）。
  - 标准 **Cache-Aside（先写 DB，再删 Cache）**：仅当「读线程 $R$ 在缓存刚好缺失时读出 DB 旧值 $v_0$ $\rightarrow$ $R$ 发生卡顿 $\rightarrow$ 写线程 $W$ 完成写 DB 新值 $v_1$ 并删完 Cache $\rightarrow$ $R$ 才醒来执行 `set(cache, v_0)`」时才会脏回填（因读快写慢，概率低但真实存在）。**根治手段**：为缓存写入绑定单调数据版本号 `version` 或 **Memcached `gets/cas` Lease Token**（写操作删缓存时递增失效租约，迟到的旧回填因 Lease 失效被拒绝），并用数据库 Binlog（Canal/CDC）异步重试删除兜底“删缓存网络失败”。

### 4.2 分片路由：虚拟节点一致性哈希与有界负载（Bounded-Load）

普通 `hash(key) % N` 在扩缩容 1 台机器时会导致接近 $100\%$ 缓存/前缀亲和瞬间失效。**一致性哈希环（Consistent Hashing）**将节点与 Key 映射到 $2^{32}$ 环上顺时针就近路由，扩缩容仅迁移约 $1/N$ 数据：
- **虚拟节点（Virtual Nodes）**：若物理节点太少（如 3 台），环上弧长极不均匀导致严重负载倾斜；为每台物理机生成 $100\sim 200$ 个虚拟节点 `hash(f"{node}#{v}")` 均匀打散在环上，配合有序数组 `bisect_left` 即可 $O(\log(N\cdot V))$ 路由。
- **有界负载一致性哈希（Bounded-Load Consistent Hashing，大模型 Prefix Cache 路由核心！）**：当大量长上下文请求共享同一 `session_id` 或热门文档前缀时，纯顺时针路由会把某台推理实例打满排队。解法：设负载上界因子 $c$（如 $1.25 \times \text{平均队列深度}$），顺时针找第一个当前排队未超上限的存活节点——兼顾高 Prefix Cache 命中率与队列削峰！

### 4.3 过载保护与尾延迟治理（Tail at Scale）

1. **三种限流原语精确取舍**：
   - **固定窗口计数器**：边界时刻存在 $2\times$ 临界突刺漏洞（如 `00:59` 放 1000 个、`01:01` 又放 1000 个，2 秒内涌入 2000 个）；
   - **令牌桶（Token Bucket）**：按恒定速率 $r$ 往容量 $B$ 的桶里补令牌，允许最高 $B$ 的合法突发流量，适合入口 API 网关；
   - **漏桶（Leaky Bucket）**：无论入口多突发，严格按固定间隔匀速流出，适合保护下游脆弱第三方接口。
2. **三态熔断器（Circuit Breaker）与负载卸载（Load Shedding）**：
   - `Closed`（正常放行并统计滑动窗口错误率/慢调用率）$\xrightarrow{\text{错误率}>\text{阈值}}$ `Open`（熔断期直接快速失败返回降级值，绝不占满线程池等超时！）$\xrightarrow{\text{冷却时间到}}$ `Half-Open`（仅放行少量探测请求：连续成功则回 `Closed`，任一失败立即退回 `Open`）。
   - **自适应并发控制（Little's Law $L = \lambda W$）**：当观测到最小 RTT 与当前排队 RTT 比值恶化（如 Vegas / Gradient 算法）时自动收缩最大并发 `in_flight` 上限，配合按优先级丢弃低优请求（Load Shedding）防止全站级联排队死锁。
3. **对冲请求（Hedged Requests）砍尾延迟**：对幂等只读请求，不在第 0ms 双发浪费翻倍算力，而是等请求超过 **P95 延迟阈值**仍未返回时才向另一副本发出第 2 个备份请求，仅增加约 `5%` 负载即可大幅削平 P999 毛刺。

## 5. GPU 体系结构与大规模 MoE / RL 训推系统全栈推导

### 5.1 参数量与训练 FLOPs 第一性手算（免死记！）

对单层标准 Transformer（隐藏维 $h$，序列长 $S$，批大小 $B$，SwiGLU MLP 中间维 $d_{ff}$）：
- **Attention 线性投影（Q, K, V, O）**：以 MHA 为例共 4 个 $h \times h$ 矩阵，参数量 $4h^2$；每次矩阵乘 `[B·S, h] × [h, h]` 包含一次乘和一次加（系数 **2**），前向计算量为 $4 \times 2 B S h^2 = 8 B S h^2$ FLOPs；注意力打分与加权 `QK^T` + `PV` 共 $4 B S^2 h$ FLOPs。
- **SwiGLU MLP（Gate, Up, Down 三个矩阵）**：参数量 $3 h d_{ff}$，前向计算量 $6 B S h d_{ff}$ FLOPs。
- **核心黄金法则（当上下文 $S \ll 6h$ 时矩阵乘占绝对主导）**：
  - 每个参数在每个 Token 的**前向传播**中贡献 **$\approx 2$ FLOPs**；
  - **反向传播**需分别对输入激活算梯度和对权重算梯度，计算量约为前向的 **2 倍（$\approx 4$ FLOPs/param/token）**；
  - 因此单步训练（无重计算时）总计算量恒定满足 **`6Ψ` 定律**（开启全量 Activation Checkpointing 重算一遍前向则变为 **`8Ψ`**）：
    $$\text{Training FLOPs} \approx 6 \times \Psi_{\text{active}} \times T_{\text{tokens}}$$
    *（注意：对 MoE 模型如 DeepSeek-V3 总参数 671B、每 Token 激活 37B，$\Psi_{\text{active}}$ 代入激活参数量 `37B`，而静态显存 `16Ψ` 代入总参数量 `671B`！）*

### 5.2 Ring-AllReduce 精确带宽推导与 5D 并行全景对比

- **为什么 Ring-AllReduce 带宽利用率与卡数 $N$ 几乎无关？**
  设梯度总字节数为 $M$，$N$ 张卡连成逻辑环并将数据均分为 $N$ 块（每块 $M/N$）：
  1. **Scatter-Reduce（$N-1$ 步）**：每步每张卡同时向下一邻居发 $M/N$、从上一邻居收 $M/N$ 并累加，$N-1$ 步后每张卡持有 $1/N$ 分片的完整全局和；
  2. **All-Gather（$N-1$ 步）**：再传 $N-1$ 步把完整分片广播到全环。
  每张卡总发送字节数为 $2\frac{N-1}{N}M < 2M$！在大消息带宽受限区，耗时 $\approx \frac{2M}{\text{单卡链路带宽}}$，不随 $N$ 膨胀；但当 $N$ 上千且消息变小时，$2(N-1)$ 步的**延迟项线性爆炸**，需切为机内 NVLink Ring + 机间 **Tree / Double Binary Tree AllReduce**（步数降为 $O(\log N)$）。

| 并行维度 | 切分对象 | 核心通信原语与频次 | 适用硬件域与关键陷阱 |
| --- | --- | --- | --- |
| **DP / ZeRO-1,2,3** | Batch 数据 + 状态分片 | ZeRO-1/2 为 `ReduceScatter + AllGather`（共 **`4Ψ` Bytes**）；ZeRO-3 前反向多两次参数 `AllGather`（共 **`6Ψ` Bytes**） | 跨机 RDMA 可跑；微批太小时通信难以被反向计算 Overlap |
| **TP + SP** | 层内矩阵列切+行切；SP 切 LayerNorm/Dropout 序列维 | 每层前向 2 次、反向 2 次 `AllReduce`（开 SP 后拆为等价通信量的 `ReduceScatter + AllGather`） | 通信在单步关键路径上，**严禁跨机跑 TP**（锁在单机 8 卡 NVLink 内）；TP 过大导致小矩阵乘降算子利用率 |
| **CP（Context Parallel）** | 超长序列 $S$ 沿序列维切分（如 Ring Attention / DeepSpeed Ulysses） | Ring Attention 环状流转 KV 块与计算重叠；Ulysses 用 `All-to-All` 在序列切分与 Head 切分间转置 | 专解 $S \ge 128\text{K}$ 时单卡激活显存爆炸；GQA 下需注意 $n_{kv} \ge \text{CP/Ulysses 度}$ |

### 5.3 推理系统深水区：RadixAttention、PD 分离与投机解码数学无损证明

1. **PagedAttention $\rightarrow$ RadixAttention（SGLang）**：
   - PagedAttention 把单请求连续虚拟 KV 页映射到离散物理块，消除外部碎片；
   - **RadixAttention** 进一步在服务端不立即销毁已完成请求的 KV 物理块，而是以 Token 序列为边维护一棵 **基数树（Radix Tree）**，将多轮对话历史、Few-shot 模板、Agent ReAct 循环前缀及树搜索分叉节点的 KV 块挂在树上做引用计数共享，显存满时按 **LRU 驱逐引用计数为 0 的叶子节点**——直接把长程 Agent 多轮交互的首字延迟（TTFT）砍掉数倍。
2. **Chunked Prefill vs PD 分离（Mooncake 架构）**：
   - 单实例混跑时，一个 32K Prompt 的 Prefill 会霸占 GPU 数百毫秒，导致同批正在生成的几十个 Decode 请求全部卡顿（TPOT 违约）。**Chunked Prefill** 将长 Prompt 切成如 `512` token 小块与 Decode 请求拼成定长预算批，平滑尾延迟但牺牲部分 Prefill 算力效率且反复搬运权重；
   - **PD 分离** 干脆将集群物理拆为**高算力配比的 Prefill 节点**与**高显存容量/带宽配比的 Decode 节点**，Prefill 算完后通过 RDMA 零拷贝引擎（如 Mooncake Transfer Engine）将 KV Cache 直接异步推入 Decode 节点显存，互不干扰各自压满算力与带宽极值。
3. **投机解码（Speculative Decoding）为什么在随机采样（Temperature $>0$）下仍能保证输出分布与原大模型 $p(x)$ **100% 精确相等**？（高频推导题！）**
   - 小草稿模型 $q(x)$ 串行猜 $\gamma$ 个 token，大目标模型 $p(x)$ 仅用 **1 次并行前向**同时算出这 $\gamma+1$ 个位置的真实分布（把 Memory-bound 变成算力白嫖！）。
   - 对第 $i$ 个草稿 token $x \sim q(x)$：
     - 以概率 $\alpha(x) = \min\!\left(1,\, \frac{p(x)}{q(x)}\right)$ **接受**该 token；
     - 一旦在某步被拒绝，丢弃后续草稿，并从修正后的**残差正部归一化分布**中重采样一个新 token：
       $$p'(x) = \frac{\max\bigl(0,\, p(x) - q(x)\bigr)}{\sum_{y} \max\bigl(0,\, p(y) - q(y)\bigr)}$$
   - **一行验证无损性**：最终采样到任意 token $x$ 的总概率等于「草稿直接抽中且被接受的概率」加上「草稿被拒后重采样抽中 $x$ 的概率」：
     $$P(\text{output}=x) = q(x)\min\!\left(1,\frac{p(x)}{q(x)}\right) + \Bigl(1 - \sum_y \min(q(y),p(y))\Bigr)\cdot \frac{\max(0, p(x)-q(x))}{\sum_y \max(0, p(y)-q(y))} = \min(q(x),p(x)) + \max(0, p(x)-q(x)) \equiv p(x)$$
     恒等成立！因此无论草稿模型多弱，**绝不损失哪怕一丝生成质量，仅影响平均接受步长与加速比**。

### 5.4 Python 标准手抄原语（三 & 四）：FlashAttention 在线 Softmax 与水位抢占 Batch 调度

$$m_{\text{new}} = \max(m_{\text{old}},\, m_{\text{tile}}),\quad \alpha = e^{m_{\text{old}} - m_{\text{new}}},\quad \ell_{\text{new}} = \ell_{\text{old}}\alpha + \sum_{j \in \text{tile}} e^{s_j - m_{\text{new}}},\quad \mathbf{o}_{\text{new}} = \mathbf{o}_{\text{old}}\alpha + \sum_{j \in \text{tile}} e^{s_j - m_{\text{new}}}\mathbf{v}_j$$

```python
import math
from collections import deque
from dataclasses import dataclass

def online_softmax_attention(q: list[float], keys: list[list[float]], values: list[list[float]], tile: int = 4) -> list[float]:
    dim, out_dim = len(q), len(values[0])
    scale = 1.0 / math.sqrt(dim)
    m, l, acc = -math.inf, 0.0, [0.0] * out_dim

    for i in range(0, len(keys), tile):
        k_blk, v_blk = keys[i : i + tile], values[i : i + tile]
        scores = [sum(q[d] * k[d] for d in range(dim)) * scale for k in k_blk]
        m_new = max(m, max(scores))
        alpha = math.exp(m - m_new) if m != -math.inf else 0.0
        p_blk = [math.exp(s - m_new) for s in scores]
        l = l * alpha + sum(p_blk)
        for d in range(out_dim):
            acc[d] = acc[d] * alpha + sum(p * v_blk[j][d] for j, p in enumerate(p_blk))
        m = m_new
    return [x / l for x in acc]


@dataclass
class SeqReq:
    req_id: str
    arrival_ms: int
    prompt_tokens: int
    generated: int = 0
    max_new: int = 16
    @property
    def kv_tokens(self) -> int: return self.prompt_tokens + self.generated

class ContinuousBatchScheduler:
    """KV 水位守恒 + LIFO 抢占最新请求（最少重算浪费）+ 首包超时防饥饿。"""
    def __init__(self, max_batch: int, max_kv: int, max_wait_ms: int = 10) -> None:
        self.max_batch, self.max_kv, self.max_wait = max_batch, max_kv, max_wait_ms
        self.waiting: deque[SeqReq] = deque()
        self.running: deque[SeqReq] = deque()

    def step(self, now_ms: int) -> list[str]:
        while self.running and sum(r.kv_tokens for r in self.running) + len(self.running) > self.max_kv:
            self.waiting.appendleft(self.running.pop())

        if self.running or len(self.waiting) >= self.max_batch or (
            self.waiting and now_ms - self.waiting[0].arrival_ms >= self.max_wait
        ):
            while self.waiting and len(self.running) < self.max_batch:
                cand = self.waiting[0]
                if sum(r.kv_tokens for r in self.running) + len(self.running) + cand.kv_tokens + 1 > self.max_kv:
                    break
                self.running.append(self.waiting.popleft())

        scheduled, survivors = [], deque()
        for r in self.running:
            scheduled.append(r.req_id)
            r.generated += 1
            if r.generated < r.max_new:
                survivors.append(r)
        self.running = survivors
        return scheduled
```

## 6. 四道综合系统设计与排障大题标准演练框架

### 演练题 A：设计支持百万并发沙箱与断网无损恢复的「长程 Agent 执行网关」
- **核心痛点拆解**：① 单任务横跨 1–20 小时，客户端必断连、网关节点滚动重启；② Agent 调用外部写接口（建 PR、扣配额、跑命令）严禁因超时重试触发重复执行；③ Prefix Cache 命中率决定了 80% 的 Token 成本。
- **高分架构四件套**：
  1. **Session 事件流与执行器物理解耦（Brain / Hands / Session Log 分离）**：网关无状态化；一切模型输出、工具调用意图与回执先落 `AuthorityStore` 只追加事件表 `(session_id, seq_id UNIQUE, event_payload)`，前端凭 `after_seq` 随时断线补齐。
  2. **CAS 租约 + Fencing Token 互斥接管**：Worker 心跳超时后，新 Worker 申请更高 `epoch` 租约；接管后先回读最后一条 `EffectIntent` 状态——已提交则直接注入回执继续推理，处于 `provider_pending` 则带原 `idempotency_key` 向外部查询对账，绝不盲目生成新 ID 重跑。
  3. **有界负载一致性哈希与 Prefix Cache 稳定契约**：System Prompt 与 Tool Schema 冻结为不可变头部；工作集更新采用尾部追加（Append-Only Delta），仅在触及上下文窗口水位时在显式 `EpochBoundary` 原子压缩换基线，路由层按 `session_id` 有界负载一致性哈希亲和到持有热 Radix KV 块的推理实例。
  4. **分级背压**：单租户并发沙箱与 Token 速率由令牌桶门控；下游推理队列超水位时拒绝低优后台巡检（HTTP 429 + `Retry-After`），保交互式前台低延迟。

### 演练题 B：设计大规模异步 Agentic RL 训练管线（消除长尾环境等待与策略陈旧度坍缩）
- **核心痛点**：同步 GRPO/PPO 等一个 Batch 内全部 512 条多轮轨迹跑完才更新一次权重；最慢 5% 的复杂编译/测试轨迹拖慢整组 GPU 空转 80% 时间（Straggler Problem）；若全异步又导致采样策略 $\pi_{\text{behav}}$ 与当前学习策略 $\pi_\theta$ 相差 $k$ 步引发梯度爆炸。
- **高分架构四件套**：
  1. **Rollout 集群与 Learner 集群完全解耦 + 可中断 Partial Rollout**：权重更新时无需杀死在跑沙箱容器，通过状态快照暂停，广播新权重后继续生成后续轮次，显式为每段 token 记录当时的 `policy_version` 与采样端精确 `behavior_logprob`（防推理引擎 FP8/算子差异与训练引擎产生数值失配！）。
  2. **有界陈旧度窗口（Bounded Staleness $\tau_{\max}$）**：消费队列校验 `current_step - traj.min_policy_step <= tau_max`；超界样本丢弃或降权，窗口内采用截断重要性采样（Truncated IS / Decoupled PPO Clip-Higher）加中心化漂移校正。
  3. **微虚机 CoW 快照分叉底座**：用块设备层 CoW（如 `OverlayBD + ublk`）从同一中间检查点在 `<100ms` 内分叉出 $G$ 条同起点分支采样组内相对优势，消除容器冷启动镜像拉取风暴。
  4. **树外防作弊验证器**：评分脚本与测试集挂载在受测 Agent 不可读写的独立命名空间/只读宿主侧，切断篡改测试或弱化断言的 Reward Hacking 通道。

### 演练题 C：千卡分布式训练集群「Step Time 偶发翻倍毛刺 / NCCL Watchdog 超时」排障决策树
1. **先分界（计算慢、通信等、数据饥饿还是宿主抖动？）**：打点每个 rank 的 `data_load_ms`、`fwd_bwd_kernel_ms` 与 `nccl_wait_ms`——**注意：90% 的“NCCL AllReduce 卡死/慢”假象，根源其实不是网络坏了，而是某 1 张慢卡（Straggler）还没算完前向/反向，导致其余 1023 张快卡全部停在集合通信屏障等它！**
2. **定位真慢卡（寻找“最晚进入 NCCL 集合点”的那个 Rank）**：检查各节点最后进入通信算子的时间戳：
   - 若某节点计算变慢：查 `nvidia-smi -q` 是否触发 **GPU 过热降频（Thermal Throttling）**、ECC 双比特显存纠错重传、宿主机 CPU 被后台日志压缩/`fork` CoW 抢占导致 Kernel Launch 断流；
   - 若所有 Rank 几乎同时进入通信却集体卡住：才是真正的 **RDMA 网络拥塞/丢包**——查交换机 PFC（Priority Flow Control）死锁风暴、RoCE ECN 水位、光模块误码重传，并用二分法跑 `nccl-tests (all_reduce_perf)` 隔离故障机架或坏卡。
3. **容错自愈**：启用异步 Checkpoint（先极速拷至宿主机 Pinned DRAM 再后台刷分布式存储）+ 弹性健康探针自动摘除亚健康节点重拉作业。

### 演练题 D：单机内存受限（如 4GB RAM）处理 1TB 日志流的精确/近似统计设计
- **精确 Top-K 频次统计（哈希分桶分治）**：不能直接建全局 HashMap（必 OOM）。第一遍流式扫描按 `hash(item) % 1024` 写入磁盘 1024 个临时分区文件（相同 key 必落同一桶，每桶均值 ~1GB，若单桶受热点倾斜仍超内存则换二次哈希盐递归再切）；第二遍逐桶读入内存精确计数并用容量为 $K$ 的最小堆（`heapq`）维护全局前 $K$ 大。
- **在线单遍近似方案（允许可控误差时）**：去重基数估算用 **HyperLogLog**（几 KB 内存 `<1%` 标准误）；高频重象（Heavy Hitters）用 **Count-Min Sketch + 小顶堆** 或 **Misra-Gries / Space-Saving** 算法，清晰对比精确两遍磁盘 I/O 成本与单遍有界误差的工程取舍。
