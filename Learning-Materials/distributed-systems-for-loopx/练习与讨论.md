# 把概念变成推理：练习、实验、讨论与四周路线

配合[补课讲义](./补课讲义.md)使用。可把每个知识点附着到一个真实失败窗口上，先建立可检验的控制面推理。

## 一、先建立一个能自检的学习标准

一个概念有四种不同的掌握程度：

1. 能认出名字，复述定义。
2. 能用自己的例子画出正常与失败时序。
3. 能实现一种修复，并解释它依赖的假设。
4. 能构造反例，说明修复在哪些情况下仍不成立。

对 timeout/unknown、事务、幂等、CAS、fencing、状态 authority、恢复与投影，建议至少练到第三层，并能指出第四层的一个边界。对 Raft/Paxos 内部证明，第一阶段以理解服务契约、故障假设和使用边界为主；后续要自主实现它们时再进入证明和完整 lab。

每次学习可以采用一个 60—90 分钟单元：读机制 20—30 分钟，画反例 15 分钟，写/跑一个实验 20—30 分钟，最后脱离原文解释 5 分钟。时长按熟悉程度调整，完成标准是产物与推理，不是读完页数。

## 二、五分钟自测

先不查资料，每题说出一个时序或具体边界。卡住是学习定位，不是能力判决。

1. 服务调用超时后，你凭什么决定重试？
2. 有唯一 operation id，为何仍可能重复扣减？
3. 数据库事务成功，为什么客户端还会不知道成功？
4. 同一行更新原子，为什么跨行约束仍可能被破坏？
5. 两个事务最后的数据库内容与串行执行一样，就一定可串行化吗？
6. lease 过期，为什么旧 worker 还能破坏状态？
7. fencing token 只在客户端检查，为什么不够？
8. 接收过一次事件，为什么仍可能出现旧投影覆盖新投影？
9. 一个纯函数返回“允许执行”，为什么提交处还要验证？
10. worker 回报 done，为什么不能直接关闭 Goal？
11. 跑过一次进程崩溃测试，能宣称掉电安全吗？
12. 一个模型检查通过，为什么实现仍可能错误？

答案分别对应讲义 1/9、9、5、6、6、10、10、11、4/7、3/15、2/8、17。比能答多少更有意义的信号，是你是否能清楚指出“我还不知道 provider 是否有这项保证”。

## 三、动手实验：先预测，再运行

实验文件：[recovery_lab.py](./recovery_lab.py)。只用 Python 标准库和临时 SQLite 文件，无网络、无密钥、无 LoopX 状态修改；程序结束后删除临时数据库。

```bash
python3 Learning-Materials/distributed-systems-for-loopx/recovery_lab.py
```

### 实验 1：同一事务成功两次，业务仍然错

初始余额 100，扣减 10 后提交，故意丢掉响应。调用方盲重试同一扣减。

先预测：数据库的 atomicity 破坏了吗？余额应该是多少？

程序输出的 naive balance 是 80。每次扣减事务都完整成功，错误来自两次业务执行。加入“operation id + payload 绑定 + 与扣减同事务的 receipt”，重试后余额是 90，而且得到第一次结果。

继续修改同一 operation id 的 amount，程序应拒绝，并维持余额。这个用例检查“同一身份不能偷偷代表新意图”。

**边界：** effect 本身就在同一个 SQLite 事务里。把扣减换成一个外部支付 API，本实验的原子性就不再覆盖它。

### 实验 2：提交前中断与提交后响应丢失

提交前抛异常，rollback 后余额仍为 100、receipt 为 0。提交后丢响应，余额为 90、receipt 为 1。

调用方都“没有得到正常结果”，远端事实却不同。请用这两个案例解释为什么 exception 不能统一映射成 `not_committed`。

**边界：** 这里的提交前异常由程序执行 rollback；提交后丢响应由受控异常模拟并重新打开连接。没有执行 kill、操作系统崩溃或断电，不能把这个实验写成掉电测试。

### 实验 3：旧 generation 写入

先把当前 epoch 更新到 8，新 owner 写入结果。一个不检查 epoch 的旧写会覆盖它；改为 `WHERE epoch = 7` 后，旧写命中 0 行，当前 epoch 8 的写仍能成功。

**边界：** authority epoch 和受保护数据在同一数据库中。这演示提交边界上的条件写，不演示跨主机 lease 服务、时钟漂移或远程资源的 fence 安装协议。

### 实验 4：乱序 snapshot

先安装 revision 11，再收到 10，再收到重复的 11。投影保持 11；相同 revision 配不同内容被拒绝。

**边界：** 每条消息是完整 snapshot。若 10 是 `+10`、11 是 `-3` 这样的 delta，丢弃 10 会算错，必须换用顺序恢复或其他协议。

### 实验 5：抽象模型中的 write skew

两位 worker 各自从同一旧快照看到“还有另一个人值班”，分别下线，结果为 0 人；串行重新判断时，结果至少有 1 人。

**边界：** 这是内存中的抽象时序模型，不是 SQLite 隔离级别的实测。用 SQLite 单 writer 行为去冒充 PostgreSQL Snapshot Isolation 的实验，会把概念学反。

### 可以自行做的三个变体

- 删除 `receipts` 的查询分支：同一操作再次扣减，观察不变量失败。
- 把 receipt 与业务变更拆成两笔事务，在中间插入异常，分别观察两种不完整状态。
- 把投影版本条件移到读阶段，写阶段无条件覆盖，然后安排两个 writer 交错，构造 TOCTOU。

第三项需要自己加入明确的并发同步点；不要用“sleep 一会儿大概能复现”代替确定的执行顺序。

本公开副本已重新运行实验并通过内置断言，输出见 [实验结果](./实验结果.json)。这里的“通过”包括成功复现反面案例，并验证对应修复；不是说 naive 实现正确。

## 四、八道故障推演题

### 题 1：查无结果，能不能重新执行？

A 发出 `op-1`，请求在网络中延迟。A 超时后，向 provider 查询 `op-1`，返回不存在。A 再次调用，随后旧请求也到达。

**请回答：** 即使查询是线性一致的，为什么仍有重复风险？最少需要再加入什么契约？

<details><summary>参考推理</summary>

查询时确实可以不存在，但旧请求未来仍可能提交。线性一致性只解释已发生的操作历史，不会把在途请求自动取消。需要 provider 原子去重同一 operation id，或先可靠终止/隔离旧尝试，再在仍有效的授权下重试。单纯轮询更多次只能增加观察，不能消除协议缺口。

</details>

### 题 2：一个字段的 CAS 为什么不够？

Worker 从 Todo version 5 读到可执行，同时从 Goal policy revision 9 读到用户授权。用户把 policy 改为 revision 10，撤销该动作。Todo version 仍是 5。Worker 用 `WHERE todo_version = 5` 提交。

**请回答：** CAS 正常工作了吗？设计错在哪里？

<details><summary>参考推理</summary>

Todo CAS 可以完全正常，但没有保护决策依赖的 policy。错误是 validation set 不完整。应将相关 policy 检查与被保护写入连接到同一个正确性边界，或使用受验证的授权代次/能力协议。不能只在提交前另做一次无保护查询，因为查询与提交之间仍有竞争。

</details>

### 题 3：两个事务没有写同一行

最多允许一个进行中的高成本实验。两个事务都查询 `COUNT(running)=0`，分别插入不同 experiment id，双方提交。

**请回答：** 唯一 experiment id 保护了什么？如何保护总数量约束？

<details><summary>参考推理</summary>

唯一键只保护 id 不重复，不保护查询谓词代表的容量约束。可用一个容量/预留行作条件更新并同事务插入实验记录，或采用足以保护该谓词的可串行化事务等机制。所有会改变不变量的路径都要遵守协议，不能只修一个入口。先调用外部实验 API 再抢名额则已经太晚。

</details>

### 题 4：token 单调就够了吗？

租约服务发出新 token 8，但受保护资源只见过 7。旧 worker 带 7 的请求先于新 worker 带 8 的请求到达。资源采用“只拒绝小于历史最大 token”的规则。

**请回答：** 旧请求会被拒绝吗？它符合哪种 fencing 保证，缺哪种更强保证？

<details><summary>参考推理</summary>

旧请求可能被接受。这个规则可防止资源已接受新 token 后的旧写回退，不能自动保证 authority 宣告移交的瞬间，资源已经知道旧 token 失效。若要求更强边界，需要可靠安装 fence 后完成移交，或在同一权威事务中校验当前 epoch 等协议。必须先定义交接的线性化/生效点，不能含糊说“lease 已过期，所以肯定安全”。

</details>

### 题 5：Outbox 发送成功，relay 崩溃

业务状态和 outbox 已一起提交。relay 发消息成功，尚未记录发送进度时崩溃。重启后又发送一次。

**请回答：** Outbox 失败了吗？怎样避免消费者重复扣减？

<details><summary>参考推理</summary>

这是 Outbox 常见的正常恢复窗口。它保留了投递责任，但通常允许重复交付。消费者需要稳定消息身份，将接收去重记录与自己的业务变更原子提交。若消费者还要调用另一个外部 provider，幂等问题会继续延伸到下一个边界。

</details>

### 题 6：用户点击 Stop，通知仍然发出

worker 的发送请求已经被外部消息系统接受，随后用户点击 Stop，控制面拒绝未来 dispatch，但这条通知最后仍然送达。

**请回答：** 一定是 Stop 实现错误吗？产品应如何表达？

<details><summary>参考推理</summary>

取决于 Stop 的承诺。阻止未来调度不代表能撤销已被接受的在途效果。需要明确当前可阻止的边界，并给出在途动作及其回查结果。若产品承诺“此刻起绝不会再有任何消息送达”，就需要外部系统共同提供更强取消协议，不能只靠 UI 改状态。

</details>

### 题 7：纯函数与两个执行者

`decide(snapshot)` 是确定、无副作用且类型完备的函数。A、B 对同一快照调用它，均得到 `claim_allowed`。

**请回答：** 纯函数有错吗？最晚在哪里解决竞争？

<details><summary>参考推理</summary>

函数可能没有错；两者对各自输入做出了相同正确判断。唯一领取必须在共享权威接受 claim 的提交边界实现，例如条件更新、唯一约束或相应事务。也可把决策与提交紧密绑定，但不能仅凭同一个纯函数就消除并发历史。

</details>

### 题 8：回放后结果一样，就证明迁移成功？

旧 Python 版本与新 TS 版本最后都返回 `done`，但新版本在中途先扣减了 quota，再发现 writeback 失败。

**请回答：** parity fixture 应比较什么？

<details><summary>参考推理</summary>

要比较领域可观察轨迹和不变量：effects 的顺序、哪些被接受、失败后是否 short-circuit、durable receipt、资源消耗、恢复身份。只比较最终状态字符串会漏掉中间副作用。若旧实现也有错误，独立语义规则应优先于无条件复制旧输出。

</details>

## 五、讨论相关交叉时，可以怎样展开

以下是讨论起点，不是需要背诵的“高阶话术”。最有说服力的表达是：先讲你系统里的具体例子，再给术语，最后交代边界。

### 1. “Agent infra 为什么会碰到数据库问题？”

可以这样开头：长程 Agent 会跨进程、跨时间修改共同状态；一旦有多个执行者和可重复到达的请求，就要处理身份、并发接受与恢复。数据库事务保护本地事实，provider 协议保护外部效果。

接着讲 LoopX 的 writeback→spend→closeout，中途崩溃如何继续。

值得追问对方：你们的 retry 是重新执行一段程序，还是恢复同一个逻辑操作？成功结果与提交记录在哪个边界绑定？

### 2. “你们为什么迁 TypeScript，还讲 FP？”

可以说：主要收益是把状态规则集中到一个 typed owner，让非法组合和遗漏分支更容易发现，决策能够从显式事实重放。Python 可以继续承载适合它的 IO 或领域 provider。

继续补一句边界：类型化和纯函数不解决外部原子性；迁移是否成功，要看真实入口的行为与恢复证据，不能只看语言比例。

追问：你们是搬代码，还是顺便减少重复决策源？桥接成本怎么测？

### 3. “LoopX 和 durable workflow 有什么区别？”

可以说：durable workflow 管理执行位置与恢复，LoopX 还需要表示当前目标、责任、权限、验收和继续执行的义务。这些层可以组合。

需要避免：把别的系统一律说成“只能跑 DAG”，或认为有语义控制面就自动获得数据库/工作流成熟度。比较应落实到具体 API、工作旅程和资格证据。

追问：目标改变以后，谁判断旧结果还能不能用？已完成步骤与当前验收条件如何绑定？

### 4. “Exactly-once 能不能实现？”

先问在哪个边界。一个数据库事务内，用唯一操作身份把效果和结果原子接受，可以建立很强的去重保证；跨任意外部 API 就要看对方参与的协议。

追问：你们说的是投递、处理还是业务效果？去重保留多久？参数冲突怎么办？丢失响应如何恢复？

### 5. “加分布式锁不就好了？”

从旧 owner 暂停后恢复的时序开始，说明资源端需要验证 fence；再区分 lease 发放与受保护写入的接受边界。

追问：token 在哪里检查？检查与写入原子吗？新 lease 发出但资源没见过新 token 时怎么办？

### 6. “CAP 是三选二吗？”

可以把问题放回具体 API：分区时，这个操作要不要继续回答？若继续，它放弃了哪种新鲜度/顺序承诺？读展示数据和修改保护性状态可以采用不同退化策略。

需要避免：把错误响应算成 CAP availability，或用“我们是 CP”替代所有接口的契约。

### 7. “CRDT 适合多 Agent 协作吗？”

可以合并的证据集合、标签、某些计数有机会采用相应结构；独占 claim、不可超卖预算和可撤销授权需要额外设计。合并数据不等于合并权限。

追问：更新是否可交换？重复合并安全吗？撤销如何表达？收敛结果是否仍满足业务不变量？

### 8. “为什么数据库默认隔离不够？”

画两位 worker 同时退出的 write-skew。然后比较条件更新共同记录、显式锁、Serializable 的成本和覆盖范围。

需要避免：笼统说“必须全开最高隔离”，或认为“写不同的行就没冲突”。

### 9. “Agent memory 和数据库是什么关系？”

可以说：memory 帮助提出下一步策略，但检索结果可能陈旧，不能直接作为授权或事实主存。需要 source、scope、revision 与当前 authority 校验。

追问：一次 memory 命中改变的是建议、证据还是执行许可？旧经验作废后，如何阻止它继续生效？

### 10. “你怎么证明系统可靠？”

说清你实际做过哪层测试：负例、提交点故障、真实后端、重复请求、恢复后的独立读回。然后明确未覆盖什么，而不是用测试总数或 PR 数量替代保证。

追问：最小 counterexample 是什么？你们是否曾故意删掉一条保护规则，检查测试能否抓到？

## 六、四周补课路线

建议每周 4—6 小时，按你已有基础调整。四周的目标是建立可靠推理习惯和一组可复用案例，不能等价于完成完整学位课程或生产运维训练。

| 周 | 主线 | 亲自完成的产物 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 不确定结果、状态机、幂等、FP 边界 | 手画三个提交/响应丢失时序；跑实验 1/2；写一页恢复决策表 | 能分清外部事实、本地认知和当前权限；不能把 unknown 归成 absent |
| 2 | 事务、并发历史、CAS、WAL | 画 write skew；解释一条条件更新；跑实验 3/4/5；对照 LoopX 一笔事务的原子范围 | 能指出跨行依赖和 TOCTOU；能区分进程崩溃与掉电 |
| 3 | 复制、一致性、lease、Outbox | 画旧 owner 恢复与新 fence 安装的时序；画发送与确认两次失败窗口 | 能给一项保证加上对象、提交点、故障模型和进展假设 |
| 4 | 实现验证、交叉表达、真实代码 | 深读 PR #5417 一条路径；写一页设计推理卡；完成一个新负例；向人讲解十分钟 | 别人能据你的描述复现反例；你能解释测试证明和没证明的部分 |

### 第一优先级：直接读这些部分

- **PostgreSQL 18 Transaction Isolation：** §13.2.1—13.2.3。先理解快照和异常，不背隔离级别表。读后画一条 write-skew 历史。[原文](https://www.postgresql.org/docs/18/transaction-iso.html)
- **AWS 幂等 API：** 请求身份、atomicity、late arrivals、same ID/different intent 四段。读后写自己 provider 的去重契约。[原文](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)
- **Distributed locking：** 暂停的客户端与 fencing 两段。读后指出 max-seen token 与当前 authority epoch 的差别。[原文](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
- **SQLite WAL：** How WAL Works、Concurrency、Checkpoint、Performance Considerations。读后说出单 writer、快照与 checkpoint 的关系。[原文](https://www.sqlite.org/wal.html)
- **Outbox：** Problem、Solution、Result context。读后画出“发送成功、确认丢失”的恢复路径。[原文](https://microservices.io/patterns/data/transactional-outbox.html)

这些值得你自己读，因为你以后要独立判断契约，而不是只消费我的结论。

### 第二优先级：用课程补齐主干

- [CMU 15-445/645 Fall 2025](https://15445.courses.cs.cmu.edu/fall2025/schedule.html)：优先 #17 并发控制理论、#18 两阶段锁、#20 MVCC、#21 Logging、#22 Recovery；再按实际问题回补 Storage、Indexes 和 Query Planning。**2PL（两阶段锁）与 2PC（两阶段提交）是不同概念。**
- [MIT 6.5840 Spring 2026](https://pdos.csail.mit.edu/6.824/schedule.html)：优先 Fault Tolerance、Consistency and Linearizability、Distributed Transactions。愿意做系统实验时再做 KV/Raft labs，不要求先完成整套课程才继续 LoopX。
- [Lamport TLA+ 课程](https://lamport.azurewebsites.net/video/videos.html)：先 1、2、5、6，学会用状态与迁移描述问题；再看 8、9、10 的 implementation、liveness、refinement。先建一个小模型，避免开局就形式化整个 LoopX。

### 第三优先级：选择性精读论文

1. [Herlihy & Wing：Linearizability](https://pdos.csail.mit.edu/6.824/papers/p463-herlihy.pdf)，先到 §3.1。目标是看懂历史与线性化点。
2. [Raft extended paper](https://raft.github.io/raft.pdf)，先 §2、§5 和 §8。目标是解释多数派、leader、已提交日志和客户端交互的关系。
3. [FLP](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)，先摘要和引言，证明可后置。目标是准确说出模型限制，不把“不可能”泛化到所有工程系统。
4. [CALM 的作者介绍](https://rise.cs.berkeley.edu/blog/an-overview-of-the-calm-theorem/)，把“新增证据”与“撤销权限”分别映射到单调/非单调判断，再考虑是否继续读论文。

第一轮暂不把 Paxos 完整证明、数据库优化器实现、跨洲事务时钟协议和通用 CRDT 设计列为必须完成项。它们有价值，但不会比把当前 effect 恢复边界讲清楚更直接地提高你对 LoopX 的判断力。

## 七、学习笔记的维护方式

每个重要概念保留四样东西：精确定义、最小反例、真实调用路径、保证边界。把事务、并发、恢复、类型与执行时权限相互链接，避免同一机制出现多套不一致的解释。

最后不看正文，用白板解释“provider 已提交、响应丢失、旧 owner 失去权限”这条轨迹，再让同伴插入一个新的故障点。
