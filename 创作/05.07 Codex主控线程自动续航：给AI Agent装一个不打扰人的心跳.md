# Codex 主控线程自动续航：给 AI Agent 装一个不打扰人的心跳

我最近用 Codex 做项目主控，有一个很真实的痛点：

不是 AI 不会干活，而是它太需要我“隔一段时间拍一下肩膀”。

比如我有一个长期推进的 Agent Harness 项目。理想状态是：我睡觉、吃饭、开会的时候，Codex 能自己看最新上下文、检查 git 状态、沿着 TODO 继续做低风险推进；如果实验还在跑，就只汇报状态，不要乱开新坑。

但实际使用里会遇到一个尴尬 tradeoff：

- 定时太短：容易打断正在执行的 agent，增加 token 消耗，也会把上下文搞得很碎。
- 定时太长：任务刚完成后可能空转几十分钟，长程推进节奏断掉。
- 手动输入“继续推进”：最稳，但这就又把人拉回了调度器角色。

所以我做了一个小工具：**Codex Thread Heartbeat**。

它的核心思路很简单：不是粗暴地每 N 分钟发消息，而是每 N 分钟先检查目标 Codex 主控线程是否真的 idle。

检查逻辑包括：

1. 找到目标 thread，例如 `agent-harness 主控` 或 `CS-Notes主控`；
2. 读取本地 Codex thread metadata 和 rollout JSONL；
3. 判断最新 user turn 后面是否已有 `final_answer`；
4. 判断是否还有未闭合 tool call；
5. 判断是否超过最小 idle 冷却时间；
6. 只有全部满足，才用 `codex exec resume <thread_id>` 发一条 heartbeat prompt。

这就把“固定定时器”变成了“带刹车的心跳”。

我现在设了两条：

- Agent Harness 主控：每 10 分钟检查一次，只有 idle 才继续推进 TAU2 / OpenViking memory 实验。
- CS-Notes 主控：每 120 分钟检查一次，做笔记系统、workflow、skill、索引治理这类低风险优化。

示例命令大概长这样：

```bash
codex-thread-queue.py install-preset agent-harness
codex-thread-queue.py heartbeat-disable agent-harness
codex-thread-queue.py heartbeat-enable agent-harness
codex-thread-queue.py heartbeat-status agent-harness
```

这里一个关键认知是：Codex App 里的“主控线程”不是一个普通 CLI 进程。它更像一条持久化 thread，App 和 CLI 都能加载它。直接拿 CLI 去 resume 同一个 thread 是可行的，但如果 App 里它还在运行，就可能产生并发写入。因此必须先做 idle guard。

我觉得这类东西会成为 agent workflow 里很常见的一层：不是让模型更聪明，而是让模型更像一个可以长期运转的工程系统。

真正的自动化不是“每 5 分钟催一次 AI”。

真正的自动化是：

它知道什么时候该继续，什么时候该闭嘴。
