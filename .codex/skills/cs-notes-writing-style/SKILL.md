# 中文技术写作

先确认读者、用途和落点。用户指定的语气与结构优先；有现成文章时只读当前项目中最相关的两三篇，不为模仿文风搜索其他工作区或私有历史。

- 先写判断，再解释机制和证据。保留作者的立场、具体经验与必要的技术密度。
- 用短句、明确主语、具体动词。避免口号、助手自我解释、空泛对比和为凑结构而重复总结。
- 将事实、推断和计划分清；实验结论保留版本、条件、指标和适用范围。不要把单次结果写成普遍能力。
- 保留重要原文、来源、公式与用户强调的抓手。调整结构不等于删掉不好压缩的证据。
- 修改长 Markdown 前先看标题树和相邻段落；优先融入原章节。真正的数学公式使用块级数学语法，代码块用于代码或字段。
- 正文面向读者，不写“用户提到”“这里应该强调”等编辑过程。未确认内容保留明确限定，不替作者编造经历。
- 表格用于可比较事实，图用于解释结构、过程或变化。图与文字应回答同一个问题；没有证据的漂亮图不构成结论。

技术方案按问题、机制、取舍、证据、下一步组织，短修改不套整篇模板。面向大众时先解释具体情境，再介绍术语；手机长图或视频仅在用户需要时选择当前可用工具，不依赖某台机器的渲染器。

修改已有协作文档，先读最新内容与评论、高亮等人工标记，再做局部修改并读回；不要用整篇覆盖抹掉协作线索。同步或发布按当前任务授权执行，写稿本身不授权发送。

持续维护飞书文档或同步本地 mirror 时，使用 [managed-lark-docs](../managed-lark-docs/SKILL.md) 的局部 patch、协作标记保护与读回流程；文风要求不扩大远端写入范围。

完成时检查：读者能否理解核心判断、证据是否支持它、重要原意是否保留、引用是否可追溯、是否混入私有来源或编辑过程。
